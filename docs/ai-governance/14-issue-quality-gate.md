# Issue品質ゲート

Issueは、第三者が理由、範囲、完了条件を検証できる追跡単位です。リポジトリ変更前に主Issueを確定し、既存Issueを使う場合もこの条件を確認します。

## 必須内容

1. 背景と目的
   - なぜ必要か、作業後にどの状態を成立させるか。
2. 根拠と不確実性
   - 確認済み事実、ユーザー提示情報、判断、仮説、未確認事項を分ける。
3. 現在と対応後
   - 現在の状態と、対応後に観測できる変化。
4. 対応範囲と非対象
   - 今回行うことと、意図的に行わないこと。
5. 受け入れ条件
   - 第三者がPass / Failを判断できる結果。
6. 検証方法
   - test、静的検査、実環境観測、文書確認など、各条件の確認手段。
7. 公開安全性
   - Issueや証跡へ出せない情報と、公開可能な要約。
8. 残るriskと未確認範囲
   - 実行できない検証、既知の制約、次に必要な確認。

外部の正本、仕様、設計資料を参照する場合は、repository、branchまたはversion、commit SHA、確認日を記録します。

## 事実と推論の分離

| 種別 | 記載する内容 |
|---|---|
| 確認済み事実 | 何を、どの証跡で確認したか |
| ユーザー提示情報 | 依頼で示された情報と、再検証した範囲 |
| 判断 | どの事実、目的、制約から方針を選んだか |
| 仮説 | 未確認であること、確度、確認方法 |
| 未確認事項 | 確認できない理由、影響、次のaction |

Minecraft、bot runtime、LLM、記憶の状態は、code上の推論だけで実環境の確認済み事実にしません。

## 既存Issueを使う場合

既存Issueが作業範囲を含んでいても、必須内容が不足する場合は、編集前に本文を更新するか、不足内容を追跡可能なコメントへ記録します。実装中に範囲、判断、既知の事実、未確認事項が変わった場合もIssueへ反映します。

## 受け入れ条件の書き方

- file作成そのものではなく、読者、tool、CI、実環境から観測できる結果を書く。
- 目標機能と実装済み機能を区別する。
- `改善する`、`対応する` だけで終わらせず、Pass / Failの境界を書く。
- 検証できない条件は、理由と残るriskを併記する。

## 公開安全性

Issueはprivate repositoryでも公開され得る文書として扱います。secret、認証情報、個人情報、実環境log原文、Minecraftの実識別子、会話全文、追跡可能なIDを貼りません。詳細は [公開安全性チェックリスト](../security-publication-checklist.md) に従います。

## Pass / Fail

次をすべて読めるIssueをPassとします。

- 理由、根拠、現在、期待する状態
- 対応範囲、非対象
- 観測可能な受け入れ条件と検証方法
- 確認済み事実と未確認事項の区別
- 公開安全性、残るrisk

変更fileだけが並ぶ、非対象がない、受け入れ条件が観測不能、未確認事項を隠す、公開禁止情報を含むIssueはFailです。必要な情報を補うまで主Issueとして実装を開始しません。
