# Issue 品質ゲート

Issueは作業メモでなく、第三者が理由、根拠、scope、受け入れ条件、riskを検証できる追跡単位です。Issueは公開物として扱い、詳細は[公開安全性checklist](../security-publication-checklist.md)に従います。

## 必須内容

1. 背景、なぜ今必要か、対応しない場合の影響。
2. 確認済み事実、ユーザー提示情報、判断、仮説、未確認事項と各出典。
3. 現在の挙動または制約と、利用者・運用・保守・data・securityへの影響。
4. 現在と対応後の体験。直接の製品体験が変わらない内部改善では、その理由と開発者・運用者の目標を分けて書く。
5. 目的と期待する成果を実装項目でなく観測可能な状態で示す。
6. 対応範囲、非対象、依存、権限境界。
7. 第三者がPass / Failを判定できる受け入れ条件と検証方法。
8. 未確認範囲、残るrisk、次の最短action。

## 事実と仮説

確認済み事実は、何をどのcode、test、公式仕様、log、実データで確認したかを書きます。ユーザー提示情報はrepository側で再確認したかを明記します。codeからの推論は仮説とし、実環境観測と混ぜません。Minecraftのゲーム内結果は、実際の観測がある場合だけ事実として扱います。

## UXの書き方

同じ対象と利用文脈で、現在ユーザーが理解・判断・操作・待機・失敗・回復していること、負担や信頼への影響、対応後にできることを対で書きます。未確認の主観や感情を事実として断定しません。調査、保守、ガバナンスで直接の製品体験変化がない場合も、その理由と後続判断への効果を明記します。

## レビュー起因Issue

レビュー指摘を別Issueで追跡する場合だけ、[レビュー指摘] title、severity、由来review、観測事実、別追跡理由、scope、acceptance、verification、公開安全性を記録します。同一PRのレビュー修正は主Issueで継続します。P0、P1、security、secret、data integrity、受入証跡の矛盾は別Issue化でblockingを解除しません。

## Pass / Fail

Passは、理由、根拠、現在と目標、scope、非対象、acceptance、verification、riskが読み取れ、事実と仮説と未確認事項が分離され、公開禁止情報がない状態です。実装pathだけ、曖昧な改善語だけ、受け入れ条件なし、未確認範囲を隠すIssueはFailです。
